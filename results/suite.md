## Kernels, briefly

- sha256: compression of 16 independent 64-byte blocks. both sides generated from one round generator (`programs/sha256/gen.rs`)
- blake3: Dean's own benchmark, `blake3::hash` of 1 MiB, run unchanged on his side. caveat: his kernel is 8-way on 256-bit slots, ours 16-way on 512-bit registers. a 16-way version on his ISA was not built; the porting agent estimates 40–50% fewer ops in the chunk phase (estimate). treat this row's ratio as an upper bound
- fieldmul: curve25519, 8 lanes × 256 sequential multiplications, radix 2^52 with madd52 on both sides. ours runs a register-only fast path and falls back to a general path when a 2^-38-probability carry condition fails, so its cu are input-dependent in theory
- sort: 256 u32 keys, both sides generated from one network generator (`programs/sort/net.rs`)
- perps: batch fixed-point risk math over 256 positions: pnl, funding, equity and a margin check per position, 5 i64 arrays in, 4 out. ours is a plain rust loop, his is generated straight-line code. memory-bound: ours does 288 single-register loads/stores, his 18 32-slot bulk transfers. Dean won this until the jit checked bounds once per run of consecutive vector loads and stores (sbpf `e0d8419`)
- matmul: int8 C = A × B, A 32×256 u8 (input), B 256×128 s8 (rodata), C i32, no requantization. 16,384 dpbusd on both sides. ours: 6×4 register tiles (24 accumulators), k loop unrolled 16. his: fully unrolled 4×2 tiles, the fastest of five shapes on the jit (his 38,094-cu variant is 18.1–18.7 µs). ours does 7,168 single-register loads, which is where the bounds-check-once change helps most
- mlp-unrolled: `programs/mlp` fully unrolled (2,108 → 1,257 cu), against `compare/dean-mlp`
- falcon, keccak, mlp: from `compare/compare.py`
- perps R1 ran on both sides while the host load rose; R2 and R3 agree

ops names: `ours=dean/variant` is the same function on both sides, `ours/variant` or `=dean/variant` exists on one side only, `(composite)` is built from several of that side's ops. `dep` is one dependent chain, `ind` is 8 independent chains.

## Method

- Host: 256 cores, shared, nothing else running from this session. Load averages (1/5/15 min):
  - R1 (dean then ours) start: 57.21, 48.51, 54.51
  - R1 end: 50.14, 49.47, 54.34
  - R2 (ours then dean) start: 50.14, 49.47, 54.34
  - R2 end: 106.82, 65.25, 59.22
  - R3 (dean then ours) start: 106.82, 65.25, 59.22
  - R3 end: 81.29, 70.72, 61.87
  - bench.sh: 81.29, 70.72, 61.87 before, 96.62, 74.46, 63.19 after
  - compare.py: 96.62, 74.46, 63.19 before, 80.95, 69.33, 62.58 after
- One warm-up pass of the whole suite (builds, caches) discarded, then 3 rounds sequentially. Each round runs every `compare/suite/<k>.sh dean` and `ours` per kernel, order dean, ours in R1 and R3, ours, dean in R2. Then `./bench.sh`, then `python3 compare/compare.py --rounds 3` (its own interleaved rounds).
- Kernel scripts: each checks every case on the interpreter and the JIT against the host reference, then times one case: mean of back-to-back runs (fresh VM, one memory mapping) per batch of about 2 ms, median of the batches. All runs `ok`.
- Ops (`compare/suite/ops.sh`, `compare/opbench`): a loop of 16 iterations x 256 instances of one op, dependent (one chain, `/dep`) and independent (8 chains, `/ind`), minus the same program with an empty body; CU = CU difference / 4096. Ops in spec.rs are checked against the native AVX-512 host reference; every other op and variant of the table (all widths of width-in-imm8 ops, bcast.* imm8 0 and max, ldn/stn n = 2, 4, 8, 12, cmp predicates, gather/scatter at the element scale with indices < 64, add.d/permb in mask modes 1 and 2; ld.m/compress/expand in mode 2, st.m in mode 1) is generated from sbpf's op table and checked interpreter against JIT on CU, result, all vector registers and memory for 3 inputs and 3 program sizes, and the measured CU against the table. 9 batches of about 2 ms per engine, median.
- 249 ops in sbpf's op table, all benchmarked.
